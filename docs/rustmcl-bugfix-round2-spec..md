## 1. 占位页面排查("后续阶段实现" / "后续接待")

**现象**: 实例管理页、下载页都显示占位文案,但侧边栏保留了入口,造成"看起来有功能,点了才发现是假的"的体验。

### 处理方式
- **1.1** 全局搜索代码库中所有占位文案(`"后续阶段实现"`、`"后续接待"`、`TODO`、`Coming soon` 等关键字),列出完整清单:哪个路由、对应哪个后端能力、是否已有后端支持
- **1.2** 分类处理:
  - 后端已支持但前端没接:**这次直接接通**(不能再拖)
  - 后端也没做:**从侧边栏隐藏该入口**,不要展示一个必然失败的按钮,等真正实现后再加回导航
- **1.3** 建立一个简单的约定:以后新页面在后端能力就绪前,不要提前加入主导航,可以先放在一个"开发中"的内部路由里自测

### 验收标准
- [ ] 全局无残留占位文案页面挂在正式导航里
- [ ] 侧边栏所有可点击项都对应真实可用的功能

**提交**: `fix(nav): 清理占位页面，隐藏未实现入口`

## 3. 启动实例时 UI 阻塞 + 报错

**现象**: "启动实例就不能做其他的事情",并伴随报错(具体报错内容需要补充,但先处理"阻塞"这个明确问题)。

### 诊断方向
- **3.1** 检查启动逻辑是否在前端主线程做了同步等待(比如 `await` 一个长时间操作但没有正确用 Tauri 的异步 command,导致 UI 卡死)
- **3.2** 正确的模式应该是:点击启动 → 立即返回(command 内部异步起子进程,不阻塞)→ 通过 `emit` 事件持续通知启动进度/游戏日志/退出状态,前端保持可交互
- **3.3** 结合本轮反馈的"crash 后退出码 255 且重复出现多次"的现象:很可能是启动逻辑被多次触发(比如按钮没有禁用导致重复点击,或者事件监听重复注册导致一次启动触发多次进程)

### 任务拆分
- **3.4** 启动按钮点击后立即禁用(直到收到明确的"已启动"或"启动失败"事件才恢复),防止重复触发
- **3.5** 排查前端是否有重复注册 `listen()` 事件监听(常见 bug:组件每次渲染都注册一次监听但没清理,导致同一事件触发多次回调)
- **3.6** 拿到实际的 crash report 内容(路径:`instances/<id>/crash-reports/crash-*.txt`)分析退出码 255 的具体原因——常见可能: JVM 参数错误、Java 版本不匹配、natives 库缺失或架构不对、启动参数拼接有误(比如某个必需参数缺失或路径包含空格未转义)。**建议先手动打开一份实际生成的 crash report 贴出关键堆栈**,才能定位具体原因,不要凭空猜测修复

### 验收标准
- [ ] 启动过程中前端界面保持可交互(可以切换到其他页面、取消启动等)
- [ ] 同一个实例不会被重复启动多个进程
- [ ] 定位到 exit code 255 的具体原因并修复,能正常进入游戏而非反复崩溃

**提交**: `fix(launch): 修复启动阻塞 UI、重复启动与崩溃问题`

## 4. 账号切换时异常登出

**现象**: "设置离线账号或微软账号后,再次点击账号居然会登出"。

### 诊断方向
- 大概率是账号状态管理的逻辑错误:比如"点击账号"这个交互本意是"查看账号详情"或"切换账号",但代码里被错误地绑定成了"登出"或者状态被意外重置
- 检查 zustand(或对应状态管理)里账号相关 store 的更新逻辑,是否有地方把"点击"这个事件和"清空当前账号"关联到了一起

### 任务拆分
- **4.1** 复现该 bug,记录具体是"点击账号头像"还是"点击账号列表某一项"触发的
- **4.2** 检查对应组件的 onClick 绑定逻辑,修正误绑定的登出行为
- **4.3** 明确交互设计:点击账号应该做什么(查看详情?切换为当前账号?),和"登出"应该是完全独立的、需要用户明确操作(比如设置页里单独的"登出"按钮)才能触发的行为

### 验收标准
- [ ] 点击账号(查看/切换)不会导致意外登出
- [ ] 登出必须是用户主动、明确的操作(单独按钮 + 建议加二次确认)

**提交**: `fix(account): 修复点击账号导致意外登出的问题`

## 5. 重复下载已下载资源

**现象**: 已经下载过的资源(assets/libraries)再次触发下载流程时被重复下载,没有走缓存校验。

### 诊断方向
- 检查 `asset_cache` 表(或对应的校验缓存逻辑)是否真的在下载前被查询,还是下载器每次都无条件重新下载
- 可能之前只是设计了表结构但下载逻辑没有真正接入这层校验("设计了但没接通"是这几轮反馈的一个规律性问题,建议后续开发时对每个"设计文档里提到的机制"都要求有对应的集成测试,而不是只测试单个函数)

### 任务拆分
- **5.1** 下载前检查本地文件是否存在 + 用之前性能优化 spec 里提到的增量校验逻辑(size+mtime,或直接查 SHA1 缓存表)判断是否需要重新下载
- **5.2** 只有文件缺失或校验失败时才发起实际下载请求
- **5.3** 加日志区分"命中缓存跳过"和"实际下载"两种情况,方便后续验证该逻辑是否真的生效

### 验收标准
- [ ] 同一版本第二次创建实例/重新下载时,已存在且校验通过的文件不会被重新下载
- [ ] 日志或前端界面能明确看到"跳过 N 个已缓存文件,实际下载 M 个"这样的统计,而不是每次都从 0 开始

**提交**: `fix(download): 修复重复下载已缓存资源的问题`

## 6. 下载流程改造:创建实例时直接下载

**建议采纳**: 把独立的"下载页面"去掉,改为创建实例流程的一部分——选完版本/loader 后直接触发下载,下载完成才算实例创建成功。这样更符合 HMCL/PCL 的交互习惯,也顺带解决了"下载页面还是占位"的问题(直接不需要这个独立页面了)。

### 任务拆分
- **6.1** 创建实例的表单流程里,最后一步改为"确认创建"→ 触发下载(带真实进度条,复用已有的 `download-progress` 事件)→ 下载完成后才把实例标记为"可用"状态并跳转到实例详情页
- **6.2** 下载中如果用户中途关闭该流程,要有明确的处理(取消下载并清理部分文件,或者允许后台继续下载,需要明确选一种行为并让用户知道发生了什么)
- **6.3** 移除侧边栏独立的"下载"入口,若有历史下载记录需求,可以在设置页或实例详情页里保留一个"重新校验/重新下载"的按钮,而不需要单独一个页面

### 验收标准
- [ ] 创建实例的完整流程里包含真实下载且有进度反馈
- [ ] 侧边栏不再有指向占位页面的"下载"入口
- [ ] 中途取消创建流程时,不会残留无用的半下载文件/僵尸实例记录

**提交**: `refactor(instance): 下载流程整合进创建实例流程`
